# 首次车站输出预览卡顿分析

日期：2026-10-30。代码：`2e9533fa370817914655ebb8b8d11f928df4c4cb`。运行环境：Factorio 2.1.23 / Space Age / mac-arm64。以下为优化前的初始诊断；优化实现和复测记录见文末。

## 测试范围

沿用 17,965 格不规则矿区，大矿机、自动并带／分带、44 路内部采集输出，连接 2 车头、4 货厢、双侧装货站。最终装货出口为 8 路。使用独立存档副本，既有设施及模组包不变。

首先执行现有 `dense-station --timing-only` 八方向／镜像组合，再在隔离源码副本中添加分段计时，分别检查相同目标首次与重复重算、矿区已应用后的独立输出、首次启用车站的缓存失效。重复重算清除目标引用以绕过“坐标完全相同则不处理”的快捷返回，确保比较的规划量相同；正常重复点击完全相同的目标可能直接返回。

## 结果

| 场景 | 累计脚本时间 | 最大单 tick 时间 | 预览完成跨度 |
| --- | ---: | ---: | ---: |
| 矿区未应用、已缓存车站配置，首次放置输出 | 608.5 ms | 341.7 ms | 2 ticks |
| 矿区已应用，首次放置独立车站输出 | 727.6 ms | 727.6 ms | 1 tick |
| 只切换车站开关、未预先等待配置重算，首次放置输出 | 1454.7 ms | 455.5 ms | 319 ticks |
| 上一行完成后，相同目标再次重算 | 561.3 ms | 325.2 ms | 2 ticks |

这些是单次原生基准中的脚本测量，不能当作完整的鼠标到屏幕延迟。基准模式不限帧；319 个游戏 tick 在正常 60 UPS 下对应约 5.3 秒的调度跨度，长帧和世界更新还会影响实际等待。其他模组、图形绘制、地图规模也会改变用户侧延迟。各阶段可能互相包含，不能把所有明细直接相加。

## 确认的原因

### 1. 独立输出仍在一个 tick 内完成全部重计算

`mpp/preview.lua` 的 `preview.tick` 对 `output_only` 连续执行 `output_preview.refresh`、预览绘制及光标更新，没有分帧。上述首次 727.6 ms 全部发生在同一 tick，足以造成明显冻结。后续两次等量重算仍为 540.9 / 601.0 ms，说明首次初始化不是唯一成本。

该首次请求的主要非重叠阶段：

- 路由总计 309.0 ms，其中入口连接寻路约 270.7 ms。
- 输出实体规格构建 88.2 ms。
- 填补地形检查 115.5 ms，即使测试场地为陆地也会遍历输出占地。
- 绘制总计 202.0 ms，其中实体校验及图层处理 156.0 ms、障碍预处理 29.8 ms、连接拓扑 16.1 ms。
- 光标更新约 8.4 ms；剩余为计数、界面及调用开销。

车站模板几何生成累计约 6.3 ms，已包含在上面的部分阶段内。

### 2. 输出实体量很大，首次需要新建大量图层

44 路采集带先长距离连到车站入口再均分为 8 路，独立输出包含 17,984 个实体规格，首次生成 19,386 个预览图层。完整矿区预览有 22,682 个实体、33,132 个图层。

现有渲染缓存能复用图层句柄，但 `mpp/preview_renderer.lua` 每次仍重建连接拓扑、收集障碍、遍历全部实体，并进行原生放置检查与图层状态比较。矿区缓存命中时，`mpp/preview_output_cache.lua` 又把未变化的矿机部分与新输出合并交给同一绘制流程。因此已有图层可复用时仍会有数百毫秒计算，首次额外承担图层创建成本。

### 3. 首次启用车站可能使整个矿区缓存失效

`mpp/preview_output_cache.lua` 的 `same_options` 除 `belt_planner_choice` 外比较全部选项。只改变 `output_station_choice` 就能拒绝已有缓存。隔离实验确认变化字段仅此一个；首次走完整矿区规划，跨度为 319 ticks，下一次走缓存更新仅 2 ticks。

该现象发生在配置变化后的矿区重算尚未完成时。若先启用车站、等待矿区预览完成，再点击输出，则可以命中缓存，仍有前述路由和绘制停顿。

输出数量会影响自动并带／分带，不能简单忽略所有车站设置。应区分真正改变矿区排布的参数与只改变车站外观／位置的参数，并按采集布局是否实际变化决定重用。

此外，`cache.complete` 遇到矿区预览中的任意 `tile-ghost` 会放弃保存缓存。这会使涉及矿区填土／地基／人工冰层的后续输出继续走完整规划。此项本轮由代码确认，未混入陆地基准数据。

### 4. 原有性能基准遗漏了一段首次等待

`tests/integration/output-performance.lua` 第一条输出测量前先修改车站设置，再调用 `preview.request`，等待矿区重算完成，之后才启用 profiler。它能测点击后的已缓存输出成本，但漏测配置切换后立即放车站时的完整矿区重算。下一轮优化应把“切换配置 → 首次输出”和“已有矿区 → 独立输出”列为独立验收场景。

## 优化优先级

1. 将独立输出的规划、规格构建和绘制纳入可取消的分帧任务，控制单帧阻塞；这会缓解冻结，但仅分帧并不保证缩短总等待。
2. 复用未变化矿区的拓扑、占地与绘制结果，只更新车站和新连接带；对同一批预览有条件复用已经完成的校验，实际应用仍重新检查世界变化。
3. 缩小缓存失效范围，保留填补图层对应的缓存信息，避免无关参数变化或矿区填补导致完整重算。实际影响产量分配和矿机排布时仍应重算。
4. 继续降低长距离入口连接的实体数与寻路成本；调整并带位置须保持既有负载范围、最终输出路数及双车道连接规则。

验收应同时记录总等待、最长 tick、缓存命中、实体数与新增图层数；不能只看平均寻路时间。

## 已实现的优化

后续优化采用相同的 17,965 格矿区和 `2e9533f` 基线，在本机已更新的 Factorio 2.1.24 / Space Age / mac-arm64 上重新进行成对比较。下方数据使用这个相同运行环境；不把初始 2.1.23 诊断数字与新环境直接相减。

- `process_grid`、`process_grid_convolution`、`layout_attempts` 已有确定性的工作量上限，普通预览每 tick 最多执行四批，遇到阶段切换立即停止。实际建造、Apply 前重新校验、寻路等步骤维持独立调度。
- 独立输出和缓存输出共用可序列化的规格构建任务，每批最多 4,096 个实体；大量碰撞占地准备和图层绘制也按 4,096 个实体分帧。取消或重新选点会取消旧任务并清理新建图层，正常／强制放置均等待预览完成。
- 寻路在一次同步搜索内复用障碍快照。独立输出按 32 格区域查询可复用实体，缓存只在同 tick 的只读预览中生效；实际建造继续查询当前实体。
- 跨 tick 构建仍重新验证障碍，但查询范围限制为当前批次的保守占地范围。已有设施的归属集合每次重新读取，只缓存不变的实体编号；矿区归属没有被当成世界静态快照。
- 填补地形先用实体中心和各原型的保守外延查询危险地块，干燥区域直接返回；存在危险地块时继续使用原有精确占地、顺序和去重逻辑。
- 矿区缓存按有效输出容量预算判断车站／均分参数。车头长度或同容量的车站切换可复用矿区；预算、负载范围、矿机、资源或世界障碍变化仍触发重算。该首次开站用例从无输出预算变为 8 路预算，因此仍需要完整重算。
- 分帧渲染中的连接形状只在单个任务内共享，避免将模块局部缓存的表引用存进持久任务，导致读档或多人加入后的共享关系不同。

新增 `station-first` 和 `station-output-only` 基准场景，均将首次请求和后续等量重算分开记录。现有 `dense-station` 保留 8 个方向／镜像用例。分帧的预算按实体数确定，不依赖机器时间，以保持多人游戏的确定性。

## 优化后首次瓶颈复核（2026-10-30）

本次只分析剩余瓶颈，未修改运行时代码。另跑两个无细分插桩的原生进程及两个隔离插桩进程，均为 Factorio 2.1.24 / Space Age。使用 `station-output-only --timing-only`，关闭入口遍历断言和快照导出。无插桩运行的包摘要仍为 `50f99535bcc792ffc4dd88575ef88ceb6203ee76e76e59a7c52fe25666d1c383`，与上轮最终实现一致。首次、重复请求的坐标和工作量一致，重复请求绕过相同目标直接返回的快捷路径。

### 先区分两种首次

1. **矿区已应用，第一次放车站输出**：主要工作是大量输出规格的构建、已有实体查找、放置检查和绘制，首次还需要创建全部图层。两个无细分插桩进程分别为首次 572.9 / 566.0 ms，重复请求分别为 534.0 / 473.5 ms 和 466.8 / 531.1 ms。均为累计脚本 CPU 时间，调度跨度均为 17 ticks；不是鼠标点击到画面就绪的实测墙钟时间。
2. **刚开启车站选项就放输出**：输出容量预算变化还会触发完整矿区规划。上轮最终实现的配对结果为 1080.9 ms、112 ticks；其中矿机候选布局累计 277.8 ms、供电布局 132.0 ms、渲染 begin+step 246.7 ms、prepare_connections 124.4 ms。路由 114.3 ms 已包含在 prepare_connections 内，不能重复相加。矿机布局执行 232 次预算批次，不能把这个次数当作候选布局数量。

本例自动并带已开启，车站从关闭变为开启时，预算从无车站限制变为 8 路，会影响矿区内部带路分配。因此该重算有真实依赖，不应简单删除缓存失效条件。

### 大量输出实体是主要工作量来源

独立输出有 **17,984 个设施规格、19,386 个预览图层**。其中车站模块（包含均分器）为 **3,878 个规格**；连接矿区与车站的部分为 **14,106 个规格**。整个输出有 **17,432 条普通蓝带**，约占规格总数的 96.9%；铁轨只有 25 段。车站最终 8 路，并不代表长距离连接只有 8 路：目前 44 路采集输出连接到车站侧均分器的 44 个入口，再在车站附近均分为 8 路。

每次请求仍会完整经过：路由 → 规格转换及共享设施查找 → 碰撞框准备 → 预览连接拓扑 → 放置检查／贴图选择 → 图层创建或复用。不同阶段多次遍历同一批规格；分帧只拆开执行，没有消除这些工作。

### 细分插桩修正了“首次主要慢在创建图层”的判断

下表是两个隔离细分运行的首次结果。插桩会增加开销并影响运行时分配时序，只用于定位阶段，不用于计算优化收益。总阶段互不重叠；子项已包含在所属阶段内。

| 阶段 | 细分进程 1 | 细分进程 2 |
| --- | ---: | ---: |
| 输出规划 start_refresh | 98.5 ms | 202.1 ms |
| 输出规格构建 step_refresh（含地形填补） | 189.2 ms | 136.6 ms |
| 渲染 begin + step | 309.0 ms | 324.7 ms |
| 全部累计脚本时间 | 605.7 ms | 672.3 ms |

关键子项：

- 原生 `rendering.draw_sprite`：首次 **55.8 / 81.1 ms**，调用 **19,386 次**；重复请求全部复用句柄，没有此项。包括图层元数据处理的 draw_layer 为首次 **95.6 / 107.8 ms**，重复 **24.6–28.4 ms**。
- 首次未缓存的 artwork 样式准备：仅 **23 种**，累计 **0.275 / 0.226 ms**。这不包括 native 绘图内部的资源处理，也不代表 GPU 上传耗时；可确认 Lua 侧贴图样式缓存冷启动不是主要瓶颈。
- 车站模板几何：首次累计 **6.9 / 5.9 ms**（各两次），已包含在路由和光标相关阶段中。模板缓存不是当前最高收益方向。
- 细分进程 2 中，共享设施查找 **17,984 次、77.1 ms**，发生在规格构建内；后两次仍为 **122.2 / 78.0 ms**。当前虽然已有同 tick 空间桶缓存，仍逐设施读取原型、构造位置键与临时候选数组。
- 原生 `surface.can_place_entity` **17,984 次、32.8 ms**；重复请求仍为 **32.2 / 29.1 ms**。渲染碰撞框批次约 **30–31 ms**，拓扑约 **16 ms**；这些不会因绘图句柄复用自动消失。

上轮带断言运行的首次渲染约 398.6 ms，占 669.4 ms 的近六成；本轮无细分插桩的一次首次渲染仅 190.2 ms。额外长耗时会落入规格构建、渲染或路由等不同阶段，不能把单次阶段差额全部解释为 native 图层创建。临时表和大批对象分配是明确的代码事实，但 GC 未被直接计时，不能断言这些波动均由 GC 造成。

### 下一轮建议的先后顺序

1. **降低逐设施规格处理成本**：对 `shared_entity` 缓存静态原型分类、空空间桶直接返回、直接遍历已有桶，减少每条带的临时表／字符串；占地框只计算一次并由后续阶段复用。坐标占地可缓存，但跨 tick 的世界障碍与实际 Apply 仍须重新校验。
2. **减少重复预览处理**：未变化的矿区与变化的连接带分别维护拓扑／图层；在世界未变化且校验语义相同的条件下复用检查结果。这个方向对含矿区预览有效，独立输出用例已经不重画矿机，不能把该收益重复计算进去。
3. **评估在矿区出口提前并带**：目前约 1.41 万个规格用于长距离连接。只有在负载上下限、允许损失、最终带数和连接正确性都满足时才缩减长距离并行带数量；需要独立布局验证，不能直接把 44 路强制压成 8 路。
4. **继续拆分同步热点以降低卡顿峰值**：寻路仍同步，一次可占 100–200 ms；矿区重算中的供电布局本例占约 132 ms。现有每批 4,096 规格也不是帧时长保证。降低批次或将寻路／供电改成增量任务可改善冻结，但需同时跟踪总耗时和调度等待，不能只追求更小的单 tick。
